# Repair Relay

> The human is the sensor. The agent is the systems thinker.

Repair Relay is an evidence-first shared repair bench built for the WebMCP Challenge. It demonstrates a workflow that neither a person nor an agent handles as well alone: diagnosing a physical device under uncertainty.

The person can inspect the real object, feel airflow, hear a rattle, read a model label behind a cover, and decide what risk is acceptable. The agent can rapidly search a structured parts catalog, enforce compatibility and budget constraints, compare tradeoffs, and stage a bounded plan. WebMCP lets both operate on the same visible page state instead of passing context through screenshots, brittle clicks, or a duplicate backend integration.

## Why this is a strong fit for WebMCP

Repair is a mixed-reality task. An agent cannot directly see behind the purifier cover, feel resistance, or safely decide that the person accepts a repair risk. A person should not have to manually cross-reference model compatibility, price, evidence, and stop conditions across a catalog.

WebMCP is the coordination layer. The page exposes small, typed tools that operate on the same state the person sees. A search tool updates the visible ranking. An observation tool adds bounded evidence. A comparison tool opens the same table. A planning tool stages an unapproved proposal. A checkpoint tool returns control to the person.

This is not “an agent clicks the existing UI faster.” The human contributes information that does not exist in the browser, and the agent turns it into a better next action. The ranking becomes materially better after human evidence arrives.

## Better user experience

- **No context split:** the agent and person share one case, one evidence log, one ranking, and one staged plan.
- **Visible causality:** every recommendation shows compatibility, confidence, and the evidence that moved it.
- **Fewer unsafe leaps:** electrical or incompatible parts are penalized even when their descriptions resemble the query.
- **Bounded agency:** tools may search, compare, record, stage, and request a decision, but they cannot approve a plan.
- **Graceful fallback:** all core actions remain usable as a normal accessible web app when WebMCP is unavailable.

## What people and agents can do together

Before WebMCP, the person had to translate every physical observation into a search query, then manually keep the browser, the conversation, and the repair plan synchronized. An agent using screenshot or DOM automation could click through the page, but it had no reliable contract for changing the application's actual state.

In Repair Relay:

1. The agent reads a compact case snapshot.
2. It searches the parts catalog with hard compatibility and budget constraints.
3. It explains which physical check would most reduce uncertainty.
4. The person performs that check and records the result.
5. The agent reranks candidates and compares the best options.
6. It stages a reversible plan with assumptions and stop conditions.
7. It requests a human decision.
8. Only the person can approve through the visible UI.
9. The agent can then read the approved plan and help verify the outcome.

The human is not a captcha or a rubber stamp. The human supplies the missing sensor data and holds authority. The agent is not a chatbot pasted beside the app. It invokes first-class capabilities that change the shared interface.

## WebMCP implementation

The project uses the imperative API. Tool definitions live in `src/tool-definitions.js`, and `src/webmcp.js` registers each one:

```js
const controller = new AbortController();
await document.modelContext.registerTool({
  name: "search_products",
  description: "Search the product catalog",
  inputSchema: searchProductsTool.inputSchema,
  execute: async (input, options) => searchProductsTool.execute(input, options)
}, { signal: controller.signal });
```

The challenge-requested catalog tool is implemented as:

```js
document.modelContext.registerTool({
  name: "search_products",
  description: "Search the product catalog",
  inputSchema: {
    type: "object",
    properties: {
      query: { type: "string", maxLength: 120 },
      model: { type: "string", maxLength: 40 },
      budget: { type: "number", minimum: 0, maximum: 10000 }
    },
    additionalProperties: false
  },
  execute: async (input) => {
    const ranked = rankProducts(PRODUCT_CATALOG, input, store.getState());
    store.dispatch({ type: "SET_SEARCH", search: ranked, actor: "agent" });
    return JSON.stringify(ranked);
  }
});
```

The live implementation also supports `AbortSignal`, bounded responses, closed schemas, sanitized untrusted observations, and `readOnlyHint` annotations.

### Tool surface

| Tool | Effect |
|---|---|
| `search_products` | Ranks at most five parts/tools and updates the candidate board |
| `record_observation` | Adds bounded physical evidence to the shared case |
| `compare_products` | Opens a visible two-to-four-item comparison |
| `stage_repair_plan` | Creates a reversible proposal with stop conditions |
| `request_human_decision` | Opens a visible checkpoint; cannot approve |
| `get_case_snapshot` | Reads a compact bounded snapshot |
| `get_approved_plan` | Reads only a decision already approved by the person |
| `run_luna_review` | Evaluates the current collaboration loop and updates the Luna panel |

## Human-only approval

There is deliberately no `approve_plan` WebMCP tool. The domain reducer rejects any approval authorization whose actor is not `human`, and the page requires a trusted visible interaction plus an explicit review checkbox. `get_approved_plan` is read-only; its name does not grant approval.

This is a product decision, not just a security disclaimer: a strong human-agent experience gives the agent meaningful work while preserving a consequential decision for the person who can inspect the physical environment.

## Luna recurring reviewer

“Luna” is a deterministic adversarial evaluator, not an unverified claim that a hidden LLM is running forever.

- In the app, it reruns after meaningful changes and every 60 seconds.
- In CI, `.github/workflows/repair-relay-luna.yml` runs on pushes, pull requests, manual dispatch, and a 12-hour cron schedule from the default branch. It publishes its suggestions to the Actions run summary and preserves both reports as artifacts.
- `npm run luna` scores six dimensions and fails on blockers such as a missing registration call or an agent approval tool.
- Its latest machine-readable and Markdown results are written to `reports/`.

## Run locally

Requirements: Node.js 20 or newer.

```bash
git clone https://github.com/JPalchak/repair-relay-webmcp.git
cd repair-relay-webmcp
npm install
npm run check
npm run serve
```

Open `http://127.0.0.1:4173`.

## Test with WebMCP

See `docs/browser-test.md`. In Chrome, enable `chrome://flags/#enable-webmcp-testing`, relaunch, and inspect the registered tools in DevTools → Application → WebMCP.

For a deterministic non-WebMCP browser check, run the normal interface or call:

```js
await window.__repairRelay.invokeTool("search_products", {
  query: "restore weak airflow with a direct-fit filter",
  model: "AP-200",
  budget: 65
});
```

The debug API deliberately exposes no approval function.

## Verification

```bash
npm run check
npm run verify:repo
```
